# Требования к харнессу соревнования

Регламент соревнования определяет условия сдачи и оценки. Архив `task-dir.zip` показывает входной формат и примеры проверок. Тексты `instruction` из архива относятся к отдельным задачам и обрабатываются харнессом в пределах их рабочих каталогов.

## Цель и критерий оценки

- Разработать харнесс кодового агента на базе openJiuwen. На финальном прогоне он получает все 100 задач и их `reward` до начала решения, сам выбирает задачи и порядок работы. Учитывать, что `reward` назначается независимо от сложности.
- Максимизировать сумму `reward` за ответы, сохранённые в пределах общего бюджета и прошедшие скрытые тесты. При равной сумме побеждает меньший расход токенов. На отборочном прогоне из двух выполнимых задач нужно решить обе в выданном бюджете.
- Оценивать ожидаемый расход до запуска решения, выявлять признаки невыполнимости и учитывать оценку вместе с `reward` при выборе задач. Ориентир 15–25% невыполнимых относится к ожидаемому составу финального набора. Все примеры выполнимы, тренировочный набор команда собирает самостоятельно.

## Вход, рабочий каталог и сдача ответа

- Точка входа обязана работать с командой жюри `python /app/run_agent.py --tasks-dir /data/tasks` из `/app`. Обнаруживать задачи по `task.json` в подкаталогах переданного каталога, пропуская служебные файлы и каталоги без задачи. Поддерживать отборочный и локальный наборы меньшего размера.
- В примерах `task.json` содержит `task_id`, `task_type`, `instruction`, числовой `reward`, а также поля `expected` и `check`. Рабочий контракт для решения использует первые четыре поля и файлы задачи. `expected` и `check` доступны только локальной проверке примеров. Работа харнесса должна сохраняться при их отсутствии. Ответы и идентификаторы примеров запрещено зашивать в логику решения.
- Рабочий каталог инструментов — `workspace/` текущей задачи, если он есть, иначе каталог самой задачи. Ограничивать чтение входных файлов, запись и выполнение команд областью текущей задачи. Временные данные харнесса размещать в `/tmp`. Входные данные и тесты сохранять, исходники менять только по условиям задачи.
- Канонический артефакт сдачи — `/data/tasks/<каталог-задачи>/answer.txt`, рядом с `task.json`. Если инструмент создал ответ в `workspace/`, харнесс переносит его в каноническое место. Для задач с правками кода сохранять итоговые изменения в смонтированном каталоге задачи до публикации ответа.
- Сохранять каждый готовый ответ сразу, до перехода сессии к следующей задаче. Записывать ответ атомарно в каталоге назначения, чтобы прерывание прогона сохраняло уже опубликованные решения. В файле оставлять только требуемый итог без объяснений, разметки и отладочного вывода.
- Регламент упоминает выходной файл и `OUT`, а приведённый `docker run` передаёт только `--tasks-dir` и монтирует `/data/tasks`. Для совместимости считать `answer.txt` в каталоге задачи обязательным. Если задан отдельный файл результатов для локального запуска, обновлять его после каждого решения с учётом одновременных записей из разных сессий. Обязательный запуск должен работать без него и без `OUT`.

## Форматы из архива

В архиве восемь задач, по две каждого типа. Таблица описывает проверяемое поведение на примерах. Формат ответа для новой задачи определяется её `instruction`.

| Тип | Что должен уметь харнесс | Что сохранять в `answer.txt` |
| --- | --- | --- |
| `math` | Выполнять вычисления без `workspace/`, соблюдать порядок операций и указанное округление. В примерах используется `python3 -c`. | Целое число (`exact_int`). |
| `search` | Читать локальные Markdown-файлы из `workspace/kb/`, находить факт в одном документе или связывать сведения из нескольких документов. | Искомое значение в исходном написании (`exact_str`). |
| `data_analysis` | Читать `workspace/sales.csv`, фильтровать строки по условиям и агрегировать нужный столбец. В примерах границы диапазона месяцев включены. | Целое число (`exact_int`). |
| `coding` | Исправлять `workspace/mylib.py` и проверять результат командой `python3 test_mylib.py` из `workspace/`. Тесты сохранять в исходном виде. | `DONE` после успешной проверки и сохранения правок (`unittest`). |

## Токены и модели

- Все обращения к LLM идут через прокси организаторов. Читать `LLM_BASE_URL` и `LLM_API_KEY` из окружения. Ключи хранить вне репозитория, образа, логов и траекторий. Локальные нейросетевые модели запрещены. Классические методы, включая регрессию и бустинг, разрешены.
- Разрешены модели `qwen3.8-27b`, `qwen3.8-27b-noreason`, `qwen3.6-35b-a3b` и `qwen3.6-35b-a3b-noreason`. Планировщик может выбирать модель на каждом вызове. Варианты `-noreason` работают без рассуждений.
- Вести единый учёт всех LLM-вызовов, включая выбор задач, оценку расхода и решение. Расход в выходном эквиваленте равен `все входные токены / 10 + все выходные токены`. Кешированные входные токены учитываются полностью. Токены рассуждений входят в выходные независимо от поля ответа API. Если API уже включил их в общий счётчик выхода, учитывать их в нём один раз.
- При параллельной работе ограничивать совокупный расход с учётом запросов в полёте. Управлять объёмом контекста и числом шагов, чтобы уложиться в бюджет и оставить время на запись результатов. При исчерпании бюджета прокси прекращает отвечать и прогон может быть принудительно завершён. Обработку отказов ограничивать по времени и числу попыток.
- Числовой бюджет и способ его передачи не указаны в команде запуска. Локальный лимит для воспроизводимых проверок можно настраивать отдельно. Его наличие не должно быть условием запуска командой жюри.

## Сборка и среда исполнения

- В корне репозитория должны быть `Dockerfile`, `run_agent.py`, `README.md` и все файлы, необходимые для сборки и работы. Зафиксировать версии зависимостей, включая openJiuwen, и тег базового образа. Версию openJiuwen выбрать по результату сборки и проверки харнесса.
- Всё необходимое скачивать при сборке. Во время прогона разрешён сетевой доступ только к прокси организаторов. Учесть `--read-only`, доступный на запись том `/data/tasks`, `--tmpfs /tmp:rw,size=2g`, `HOME=/tmp`, `--cap-drop ALL`, `--security-opt no-new-privileges` и `--pids-limit 512`.
- Ограничивать параллельность пятью одновременными сессиями, укладываться в 16 ГБ RAM и работать без GPU. Проектировать под 4 CPU по тексту регламента. В приведённой команде запуска указано `--cpus 8`, поэтому приёмочный прогон на 4 CPU проверяет более строгое ограничение.
- Сборка должна укладываться в 1000 секунд, прогон — в один час. Размер сдаваемого репозитория меньше 100 МБ без `.git`. Размер собранного образа по `docker images --format "{{.Repository}}:{{.Tag}} -> {{.Size}}"` меньше 4 ГБ. Для нескольких образов ограничение применяется к их суммарному размеру.
- В `README.md` описать сборку, запуск командой жюри, размещение ответов, учёт и оценку расхода, выявление невыполнимых задач, сбор и использование тренировочных траекторий, а также воспроизводимую локальную проверку.

## Приёмка результата разработки

1. Собрать образ из чистой копии сдаваемого репозитория, проверить размер и отсутствие секретов. Запустить точку входа с параметрами жюри и файловой системой в режиме `--read-only`.
2. Прогнать все восемь примеров на копии архива с удалёнными из входных `task.json` полями `expected` и `check`. Проверять результаты отдельно по оригинальным метаданным. Проверить точный формат и расположение `answer.txt`, сохранение правок кода и успешный прогон неизменённых тестов для `coding`.
3. Прогнать две выполнимые задачи в одном запуске с общим заданным бюджетом и проверить оба ответа. Отдельно проверить учёт входных, выходных и reasoning-токенов при параллельных вызовах и сохранность уже записанных ответов при отказе прокси или прерывании процесса.
4. На самостоятельно собранном наборе с выполнимыми и невыполнимыми задачами измерить сумму баллов, расход токенов и время. Использовать эти показатели для сравнения изменений планировщика. Скрытые тесты финального набора выполняет жюри.
5. Для сдачи разместить репозиторий на GitHub или GitFlic. Для приватного репозитория обеспечить доступ `promsoft` и `madrugado` к моменту закрытия соревнования. Жюри оценивает последний коммит на этот момент. Для допуска к финальному прогону требуется пройти проверку безопасности, собрать образ и решить обе отборочные задачи.
