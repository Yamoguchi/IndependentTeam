# Этап 12 · Достаточность данных для обучаемого оценщика

**Контрольная точка по достаточности пройдена. Данных для обучения и отложенной проверки недостаточно.** В рабочем режиме используется существующая оценка: медиана сопоставимой группы при наличии истории, консервативная оценка при редких сочетаниях и нулевой токенный расход для LOCAL. Историческая вероятность успеха доступна планировщику при наличии как минимум 20 сопоставимых живых наблюдений в группе. В проверенных прогнозах вероятность отсутствует. Конкурсный запуск по-прежнему использует конфигурацию этапа 11.

## Источники и независимость

Аудит сопоставляет `results-by-task.jsonl` с отдельным `score.jsonl`. Для новых журналов требуются непрерывная последовательность и сверка итогов расхода. Для исторического прогона используется проверенный импорт со сверкой вызовов с итогами задач. Повторные отчёты одного `run_id` учитываются один раз. Подсчёт полных попыток включает терминальные исходы `submitted`, `step_limit`, `no_answer` и `generation_failed` при подтверждённом результате проверяющего и полном учёте расхода. Задачи без допуска, с прерванным бюджетом и со сбоем прокси учитываются отдельно. Метка `passed` проверяет ответ. Метка `solvable` показывает выполнимость там, где её независимо зафиксировали.

Единица подсчёта задач — `task_id`. У 43 задач из маркированных живых прогонов обнаружено 43 пары идентификатора и хеша инструкции. Для разбиения на выборки единицей должно быть семейство задачи. Ручная группировка даёт архиву девять семейств, включая пять арифметических шаблонов, два вида запросов к Markdown-базе, одну агрегацию CSV и один формат правки одиночной функции Python. У 17 дополнительных задач есть 13 новых семейств. Варианты перебора цифр и случаи отсутствующего обязательного файла сгруппированы попарно. Пилотная фильтрация CSV и двухшаговый поиск включены в соответствующие архивные семейства. Покрытие 22 семейств рассчитано до объединения связанных семейств с общей базой знаний или генератором в блоки для итогового разбиения.

Из 61 маркированного живого манифеста один без полного комплекта исключён, восемь отчётов оказались повторными представлениями. Исторический baseline пересекается с живыми пилотами по 26 задачам. Журналы без маркировки источника исключены, кроме указанного импорта. Старые локальные файлы `.runtime` содержат ту же восьмёрку публичных задач без сопоставимых признаков и настроек. Число семейств HTTP-двойника отражает лишь пересечение с ручной группировкой живых задач. Его расходы и исходы задаются сценарием, поэтому они подходят для регрессий стенда и исключены из выборки обучения и оценки переноса.

## Покрытие маршрутов, типов и ошибок

В таблице учитываются только 52 маркированных живых прогона. Каждая ячейка показывает **полные попытки / уникальные задачи / уникальные задачи с полным неуспехом**. Одна задача может появляться в нескольких маршрутах. BASELINE включает одиночную модель с выключенной маршрутизацией в нескольких режимах.

| Тип | BASELINE | LOCAL | CHEAP_LLM | SMART_LLM | CASCADE |
| --- | ---: | ---: | ---: | ---: | ---: |
| math | 75 / 11 / 3 | 4 / 1 / 0 | 7 / 3 / 1 | 4 / 1 / 0 | 7 / 3 / 0 |
| search | 62 / 13 / 1 | 4 / 1 / 0 | 8 / 2 / 0 | 0 / 0 / 0 | 0 / 0 / 0 |
| data_analysis | 53 / 9 / 1 | 4 / 1 / 0 | 5 / 2 / 1 | 0 / 0 / 0 | 5 / 2 / 0 |
| coding | 54 / 9 / 0 | 0 / 0 / 0 | 8 / 2 / 1 | 0 / 0 / 0 | 0 / 0 / 0 |

На LOCAL есть 12 успешных повторов трёх задач с нулевым расходом. На CASCADE зарегистрированы два реальных перехода после исчерпания шагов начальной модели в стресс-пилоте с однократным начальным шагом. Обе задачи успешно сданы после перехода. SMART_LLM покрывает только одну задачу math. У `qwen3.8-27b-noreason` 254 из 288 полных LLM-попыток. У трёх альтернативных начальных моделей соответственно 14, 10 и 10 попыток и ноль полных неуспехов.

Из 51 непрошедшей строки 20 относятся к полным попыткам. Это 14 исчерпаний шагов и шесть сданных ответов, отклонённых проверяющим. На одну повторявшуюся архивную задачу math приходится 13 из 20 неуспехов. Ещё 31 строка включает 14 остановок по бюджету, 11 незапущенных задач, четыре пропуска и два сбоя прокси с неизвестным полным расходом. Эти строки важны для оценки политики допуска и надёжности. Их нельзя использовать как метки исхода полного решения или приписывать им нулевую полную стоимость.

При совпадении SHA-256 текущего `run_agent.py` есть четыре живых прогона одной модели в B+C с маршрутом BASELINE. Это две пары F/G с 24 строками по одним и тем же десяти задачам, включая повтор двух задач в отборочном сценарии. Полные измерения получены на десяти уникальных задачах. F предпринял полные попытки для обоих заведомых блокеров, G остановил их до обращения к модели. На восьми выполнимых задачах не зарегистрировано ни одного полного неуспеха. Coding и альтернативные маршруты в этой когорте отсутствуют. Даже с объединением прежних ревизий крупнейшая сопоставимая группа `тип × маршрут × начальная модель × настройки` содержит 13 задач. В ней один полный неуспех.

## Признаки и качество текущих прогнозов

Для следующего исследования доступны до решения тип задачи, длина инструкции, число, суммарный размер и расширения файлов, флаг ограничения обхода, признаки операций и вычисленная сложность. К ним можно добавить заранее выбранные маршрут и модели, лимиты генерации и шагов, флаги режима, размер запроса и резерв первого вызова, локально проверяемые признаки обязательных предпосылок. Награда нужна для приоритета и подсчёта баллов. По регламенту она назначается независимо от сложности. Идентификаторы и хеши нужны для разбиения и проверки происхождения. Результаты инструментов, фактические эскалации и расход, причина терминального исхода, независимая выполнимость и проверка ответа относятся к меткам и диагностике после попытки. Самооценка модели в прогнозе вероятности не использовалась.

Из 300 полных маркированных живых попыток 90 имеют записанные признаки маршрута или плана. У 34 полных попыток есть сохранённый прогноз стоимости, из них 11 с групповой медианой и 23 с консервативной оценкой. У всех 34 стоимость положительна. На текущем коде доступны следующие описательные ошибки консервативной оценки. Пара повторно использует две задачи смешанного набора, а выборки F и G различаются по допуску блокеров.

| Когорта текущего кода | Полных прогнозов MAE / MAPE | Уникальные задачи | MAE, выходной эквивалент | MAPE |
| --- | ---: | ---: | ---: | ---: |
| F | 12 / 12 | 10 | 790,26 | 165,43% |
| G | 10 / 10 | 8 | 665,27 | 219,53% |

Показатели описывают сохранённые попытки. Для парного сравнения оценщиков на отложенных семействах размер обучающей и тестовой выборок равен **0 / 0**. Обучение не запускалось. Brier Score, Log Loss и калибровка **N/A**, поскольку в сохранённых живых прогнозах нет ни одной числовой вероятности. Изменение баллов и расхода от нового оценщика **N/A**, поскольку кандидата и отложенного прогона нет. Кривые этапа 11 характеризуют существующие конфигурации и HTTP-двойник.

Архив полностью выполним и содержит однотипные шаблоны. Повторные пилоты сосредоточены на известных проблемных задачах и меняют подсказки, пределы или маршруты. Ограниченный бюджет отбирает задачи по очереди и цене первого вызова, поэтому полного расхода для пропущенных задач нет. Маршрутизация назначает модели с учётом сложности, а переключение G меняет и допуск, и подсказку. Два блокера в текущем пилоте дают примеры остановки. Для оценки естественной частоты ошибок нужны неуспехи на выполнимых задачах. Исторические попытки характеризуют прежние версии харнесса.

## Критерии возобновления исследования

Следующие числа — предложенный стартовый минимум для простых моделей и парной проверки по семействам. При широких интервалах неопределённости объём выборки нужно увеличить.

1. Собрать на зафиксированной версии не менее 120 уникальных задач из 15 семейств для обучения и настройки и 40 задач из шести других семейств для отложенной проверки. Все версии входа, повторы и маршруты одной задачи или связанного семейства помещать в один раздел. Для F сейчас доступны десять задач из десяти семейств с полным расходом. Даже при использовании всех десяти не хватает минимум 150 задач и 11 семейств для этих двух разделов.
2. Для классификации получить минимум 20 независимых успешных и 20 неуспешных исходов в обучении, минимум по 10 в отложенной проверке. Собирать неверные ответы и полные неудачные попытки на выполнимых задачах всех четырёх типов. Сейчас их в целевой когорте ноль. Отдельно нужны новые блокеры и сложные выполнимые задачи с похожими признаками. Пропуски по бюджету, временные отказы и неизвестный расход маркировать отдельно.
3. Для каждого LLM-маршрута, который будет использовать оценщик, иметь хотя бы 20 положительных полных цен в обучении и 10 в отложенной проверке. Покрыть каждый применимый тип в обоих разделах. Сейчас в актуальной когорте отсутствует coding и есть только BASELINE. Нужны живые измерения CHEAP_LLM, SMART_LLM и CASCADE с успешными и неуспешными исходами, включая естественные случаи перехода и случаи без выигрыша. LOCAL проверять на свежих семействах по успеху и локальному времени. Токенный расход LOCAL по контракту равен нулю.
4. Фиксировать конфигурацию, признаки, прогноз, точный usage и независимый исход. Чтобы уменьшить отбор по бюджету, сначала измерять полные попытки под отдельным лимитом сбора, затем выполнить парные ограниченные прогоны на свежих копиях отложенных задач. Сравнить медиану с простой регрессией стоимости, а сглаженную частоту с регуляризованной логистической регрессией. Для ошибок стоимости указать MAE и MAPE с размерами знаменателей. Для вероятности указать Brier Score, Log Loss и калибровку с численностью по интервалам. Оценить разброс по семействам. Решение о включении принимать по подтверждённым баллам при одинаковых лимитах и по расходу при равных баллах.

Оценщик и параметры для доставки в образ не приняты. Повтор конкурсной сборки и матрицы этапа 11 относится к последующему принятию новой конфигурации. Живые вызовы для этого аудита не выполнялись.

## Воспроизведение

```bash
mkdir -p "$PWD/logs/stage-12"
EXP=$(mktemp -d "$PWD/logs/stage-12/review.XXXXXX")
.venv/bin/python scripts/stage12_audit.py --output "$EXP"
.venv/bin/ruff check scripts/stage12_audit.py
.venv/bin/python -m pytest -q
```

Аудит читает манифесты прежних этапов, сверяет независимые оценки и сохраняет метаданные, прогнозы и исходы в `observations.jsonl`, сводки по типам, моделям, маршрутам, настройкам и срезам планировщика в `coverage.json`. Для исторического baseline используется `logs/stage-01/baseline-100`. Тестам HTTP-двойника нужен доступ к локальному loopback.
