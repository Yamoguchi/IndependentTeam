# Артефакты локального стенда · версия 1

## Каталог прогона

`benchmark.py prepare` создаёт новый каталог. В `tasks/` попадают только каталоги задач с верхнеуровневым `task.json`. В нём остаются `task_id`, `task_type`, `instruction` и `reward`. Старые `answer.txt` исключаются на любой глубине. Также исключаются скрытые служебные файлы и `__pycache__`. Перед запуском стенд сверяет все подготовленные файлы и отклоняет изменённую копию. После запуска в `tasks/` остаются опубликованные ответы и изменения исходников. Проверка сверяет исходный набор с отпечатком подготовки и читает эталоны из отдельно переданного источника. Для проверки `unittest` исходный `test_mylib.py` должен совпасть по байтам с эталонным, а его выполнение в песочнице должно завершиться успешно.

| Артефакт | Содержимое |
| --- | --- |
| `run-manifest.json` | Версия схемы и формат токенов, метаданные подготовки, идентификатор ревизии и dirty-флаг, SHA-256 каждого файла харнесса и стенда, каталог задач и отпечатки входов, параметры запуска, образ, ограничения, модель, внешний лимит, коды завершения, версии из трассы и состояние журналов. Если указан baseline, сохраняется снимок его сводки для автоматического сравнения после проверки. При локальной оценке также фиксируются версия и отпечатки проверяющего кода и эталонных метаданных. |

| `tokens.jsonl` | Для новых прогонов одна строка `event: call` на попытку по `run_id` и `call_id`, включая незавершённые и отклонённые. Содержит `proxy_usage`, оценку резерва, нормализованные счётчики и статус. Строки подтверждённого отказа до отправки имеют `calls: 0`. | `score.jsonl` | Создаётся при независимой проверке или переносится из исторического прогона. Строки `task_id`, `passed`, `score` и финальная строка `tasks`, `correct`, `score`, `max_score`. |
| `comparison.json` | Baseline, совпадение очищенного набора, значения метрик, абсолютная разница и проценты относительно baseline. Сокращение входного контекста вычисляется для одинакового набора при полном учёте обоих прогонов. |

Новые запуски сохраняют отдельно `journal/trace.jsonl`, `agent-stdout.jsonl` и `agent-stderr.log`. У запуска без эталонов поля независимой оценки равны `null`. Для восстановления после жёсткой остановки `report --source-run OLD --run-dir NEW` читает доступный префикс журналов и замечает опубликованные файлы в `tasks/`, даже если агент ещё не записал событие публикации. Отбрасывается только недописанная последняя строка JSONL. Исходные каталоги при повторной генерации остаются доступны для проверки. `check` запускается после остановки агента и публикует результаты в каталоге оцениваемого прогона.

## Отпечатки и расход

`input.tree_sha256` вычисляется по байтам `input-files.jsonl`. Каждая строка записывается UTF-8, с отсортированными ключами, без пробелов-разделителей и с завершающим LF. `input.content_sha256` использует ту же схему и каноническую сериализацию четырёх полей `task.json`. Для исторического импорта `tree_sha256` восстанавливается с форматом JSON прежней подготовки и сверяется по сохранённым `task.json`. `historical_unfiltered_tree_sha256` относится к старому инвентарю с эталонными метаданными. Для сравнения старого и нового прогонов используйте `content_sha256`. При разных наборах абсолютные значения и разницы остаются видны, а эффект изменения режима по ним оценивать нельзя.

Импорт сверяет архив, старый инвентарь, каждый входной файл, контрольные суммы снимка, отпечатки харнесса, образа и списка зависимостей. Итоги из строк по задачам сверяются с итоговой строкой. Если присутствует историческая трасса, её вызовы также сверяются с агрегатами. Для старых каталогов с `tokens.jsonl` и без манифеста импорт восстанавливает состав задач из сохранившихся метаданных и строк журнала. Отпечаток исходных входов и версии имеют значение N/A, если подтверждение отсутствует. В новых прогонах источник расхода — только события отдельных вызовов. Итоги stdout используются для контроля полноты.

Выходной эквивалент считается в десятых как `input_tokens + 10 * output_tokens` с делением на 10 при выводе. Кешированный вход входит во входной полностью, а reasoning выводится отдельной метрикой и уже учтён в нормализованном выходе. При неполном журнале или пропусках usage полный `output_equivalent` равен `null`. `measured_output_equivalent` отражает наблюдаемую измеренную часть. Покрытие usage считается по наблюдаемым вызовам. Начатый вызов без завершения даёт один вызов с неизвестным расходом. Локальные баллы и факт публикации учитываются отдельно от официальной оценки.

Начиная с этапа 02, `llm.started` фиксирует резерв до передачи запроса транспорту. `llm.denied` фиксирует отказ локального допуска. Для восстановления отчёта начатый вызов без `llm.finished` получает `usage_status: "unknown"` и полный резерв переносится в `held_tenths`. Эта часть также видна в `budget.recovered_in_flight_tenths`. В работающем агенте `in_flight_tenths` учитывается отдельно от удержанного резерва завершившихся вызовов. Занятый локальный лимит включает `measured_tenths` и оба вида резерва. Отдельные поля показывают превышения оценок по компонентам, превышение лимита и число отказов. Неполный `usage` может дать измеренную часть и удержанный остаток в одной строке. У исторических прогонов поля резервов имеют значение N/A.

В режимах A и B `tool.finished` с `status_source: "harness"` различает `ok`, `error` и `invalid`. В частности, ненулевой код выхода Python означает ошибку. В B событие `context.selected` связывается с задачей и номером шага. В нём записаны размеры окна SDK до и после отбора, число исключённых групп и остаток локального бюджета. Событие может предшествовать отказу в допуске. Для измерения размеров отправляемых сообщений и схем используется `llm.request` на границе HTTP, для токенов полного запроса — `llm.finished.proxy_usage`. В отчётах `test-double` счётчики токенов заданы двойником.

В `B+C` и `B+C+D` события `tool.output_compacted` содержат размер до компактного представления, объём сохранённых данных, размер превью и признак повтора. `tool_output_bytes` суммирует UTF-8-байты строковых результатов `tool.finished` до отбора окна, включая успешно выданные детали. `detail_requests` считает все начатые вызовы `output_details`. Размеры повторной передачи в контексте учитываются отдельно.

`generation_truncations` считает ответы с `finish_reason=length`. `generation_recoveries` считает отправленные запросы восстановления, а `generation_recovery_denials` — отклонённые по локальному резерву. В строках вызовов есть исходная причина завершения прокси, профиль и причина отклонения генерации при наличии.

С этапа 06 событие `answer.validated` содержит `format` и `semantic` с отдельными статусами и причинами, `source` и решение `accepted`. Метрики считают попытки валидации, включая отклонённые кандидаты. Источники публикации `submit_answer`, `direct` и `workspace` считаются по `answer.saved` после записи файла. При прерывании между заменой файла и записью события факт публикации восстанавливается по каноническому файлу. Вердикты харнесса и независимые баллы хранятся в разных полях.

С этапа 07 `route.selected` записывает маршрут, модель, признаки, парные измерения и доступный бюджет. `route.fallback` обозначает переход от отклонённого локального кандидата к LLM. Локальная публикация использует `source: "local"`. `route.attempt_started` и `route.attempt_finished` отмечают начальную или вторую попытку. В завершении есть статус, причина отклонения кандидата и состояние правок с относительными путями, ревизией и отпечатками исходников. `route.escalation_decision` хранит исход первой попытки, оценку вероятности, будущие расходы, ожидаемую выгоду и резерв. `route.escalated` отделяет расходы двух попыток по порядковым номерам событий. Содержимое передачи модели представлено в журнале размером и отпечатком.

`results-by-task.jsonl` содержит `route`, `routing`, `attempts`, `escalation_decision` и `escalation`. `metrics.routes` считает распределение задач, начальных и вторых моделей. В `models` учитываются отправленные запросы по моделям. Доля эскалаций использует маршрутизированные задачи как знаменатель. Доля локальных решений доступна среди входов и среди подтверждённых решений. Переход без прироста означает, что переход состоялся, но независимая оценка не дала положительных баллов. Переходы с неизвестной оценкой указаны отдельно. Расход до и после перехода суммируется только по эскалированным задачам и сохраняет поля измеренного и неизвестного расхода.

## Метрики этапа 01

- **Качество и расход.** Доля успеха использует все задачи входного набора как знаменатель. Распределение расхода по задачам включает начатые задачи с известной стоимостью. Расход на успешную задачу использует расходы локально подтверждённых задач, расход на балл — расход всего прогона. Доля лимита и остаток доступны при заданном внешнем бюджете и полном учёте.
- **Контекст.** Первые и повторные входы разделяются по наблюдаемому порядку вызовов каждой задачи. Суммы и распределения используют вызовы с usage. Отдельно считаются размеры запросов и ответов в байтах. Повторная передача считается по отпечаткам сообщений и схем инструментов, уже наблюдавшихся в предыдущих запросах задачи. Байты служат самостоятельной метрикой.
- **Инструменты.** Учитываются наблюдаемые вызовы, завершения, статусы SDK, время, объём вывода и повторы одинаковых аргументов внутри задачи. Частота ошибок использует завершённые вызовы как знаменатель. В частности, строковый вывод Python с ненулевым кодом выхода может прийти как успешный вызов SDK.
- **Маршруты, планирование и ранний отказ.** Наблюдаемый порядок задач доступен с этапа 01, решения маршрутизатора и модели доступны с этапа 07. Поля планирования заполняются при запуске с `--planner`. Разметка раннего отказа относится к этапу 10.
- **Время.** Полное время агента и время запуска измеряются отдельно от суммы времени модели и инструментов. При прерывании время агента может быть неизвестно. Сохраняется длина наблюдаемого префикса трассы. Распределения содержат число наблюдений, сумму, среднее, медиану, максимум и P90 либо P95 по методу ближайшего ранга. Суммарные длительности вызовов относятся к записанным завершениям и при параллельном исполнении могут пересекаться.
- **Сравнение.** Для каждой сравниваемой метрики доступны абсолютные значения и изменение в процентах при ненулевой базе. `null` в JSON представлен как N/A в отчёте. Причины включают отсутствие события, незаписанное завершение, отсутствие независимой проверки, нулевой знаменатель и ещё не подключённые механизмы.

## Траектории планировщика F

Единица наблюдения для обучения — задача в конкретном прогоне. Связывайте план с результатом по `run_id` и `directory`, а фактические вызовы с начатой задачей по `task_index`. Сквозной порядок записей определяет `sequence`. Итоги проверки присоединяются по `task_id`.

`session_id` связывает события задач, модели и инструментов со слотом выполнения. Слот может последовательно обработать несколько задач. Для связи с конкретным запросом используйте `run_id` и `call_id`. Итоги содержат заданное число сессий и пик одновременно занятых слотов. `llm.waiting_for_budget` отмечает временный дефицит резерва до отправки. В завершении вызова `budget_wait_ms` входит в `duration_ms` и также суммируется отдельно. Онлайн-трассу и строки stdout записывает цикл событий. `results-by-task.jsonl` строится после прогона по трассе, опубликованным ответам и независимой оценке.

| Источник | Поля |
| --- | --- |
| `planning.task` до первого `task.started` | `task_type`, `reward`, `input_index`, `planned_index`, отпечаток инструкции, начальный маршрут и модель, причина маршрута и метод локальной проверки при наличии. |
| `planning.task.features` | Длина инструкции, число и суммарный размер видимых файлов, расширения, признак ограниченного обхода, признаки операций и балл сложности. Обход ограничен 128 позициями, служебные файлы и ссылки исключены. |
| `planning.task.forecast` | Прогноз и допуск в десятых долях выходного эквивалента, резерв первого запроса, локальное время в мс, компоненты запасного прогноза, источник и размер выборки, идентификаторы исторических прогонов и настройки сопоставимости. Вероятность записывается числом или `null`. |
| `planning.ready` и `planning.decision` | Исходный и плановый порядок всех задач, время построения плана, допуск или причина пропуска, измеренный расход, удержанный резерв, резерв запросов в полёте и остаток в момент решения. |
| `task.finished`, `tokens.jsonl`, `score.jsonl` | Статус и остаток после попытки, расход и покрытие `usage`, исход независимой проверки и локальные баллы. |
| `results-by-task.jsonl` | Объединённая строка с планом и отдельными полями факта. `local_ms` измеряет время попытки за вычетом времени модели и включает накладные расходы харнесса. `actual_cost` равен `null` у пропущенной задачи или при неизвестном полном расходе. |

`benchmark.py planning-history` экспортирует JSONL версии 1 из отдельно проверенных прогонов с непрерывной трассой и сверенными итогами. Запись содержит `source_run_id`, `proxy_kind`, `task_id`, `instruction_sha256`, `task_type`, `route`, `model`, `smart_model`, `settings`, `exact_tenths`, `local_ms` и `passed`. Экспорт включает полные попытки с измеренным расходом и известным исходом, в том числе неуспешные. Пропуски, отказы бюджета, ошибки прокси, обрывы и смены начального маршрута исключаются. Переход внутри запланированного каскада входит в его полный расход.

Для последующего обучения используйте только признаки из плана как вход модели. Статус, подтверждение, расход и время попытки служат метками. Разделяйте выборки по задачам или семействам до подбора параметров. F дополнительно исключает из истории совпадающие идентификаторы и отпечатки инструкций всего текущего набора и оставляет одно наблюдение на отпечаток в сопоставимой группе. Настройки сопоставимости включают режим, лимиты генерации и шагов, прямую публикацию и параметры каскада. Данные двойника пригодны для проверки механики оценки стоимости. Вероятность успеха использует только независимо проверенные исходы с прокси организаторов.

MAE выражен в выходном эквиваленте, MAPE — в процентах. Отчёт показывает их отдельно для всех известных положительных расходов и для завершённых попыток. Измеренный расход прерванной по бюджету попытки полезен для анализа допуска, а полный расход до решения неизвестен. Ошибки допуска, превышения прогноза на задачу и превышения локального лимита учитываются отдельно.

## Распознавание выполнимости G

- `recognition.checked` фиксирует длительность проверки обязательных предпосылок. `recognition.outcome` сохраняет `resolution.status`, `resolution.reason`, `resolution.evidence`, накопленный по задаче `usage`, состояние общего бюджета и признак окончательного исхода. Решения до вызова модели привязываются к каталогу, попытки в ReAct — также к индексу задачи. F пишет те же итоговые поля для выполненных и пропущенных задач.
- `recognition.retry_decision` сохраняет эвристическую вероятность успеха, будущий расход, ожидаемую отдачу и остаток с учётом запросов в полёте. `recognition.retry_admission` проверяет остаток перед повтором. `task.resumed` сохраняет прежний индекс задачи. Следующий итог использует суммарный расход обеих попыток. Незапущенный после прерывания повтор оставляет предварительный исход с `resolution_final: false`.
- Независимый `score.jsonl` может содержать булево поле `solvable`. Отчёт переносит его в `results-by-task.jsonl` вместе с исходом и основанием. `DONE` отражает наличие сданного артефакта, `passed` — результат независимой проверки. Для обучения сохраняйте обе величины.
- `metrics.json.early_stop` сводит исходы, причины, повторы, время предварительной проверки и расход до отказа. Отказ — один из `UNSOLVABLE_CONFIRMED` и `UNSOLVABLE_SUSPECTED`. Доля ошибочных отказов равна числу отказов от выполнимых задач, делённому на число всех отказов. Для этой метрики нужны метки для каждого отказа и ненулевой знаменатель. Измеренная часть и удержанный резерв указаны отдельно. Расход на задачи с меткой `solvable: false` позволяет сравнивать F и G даже при разной классификации этих задач.
