# Харнесс openJiuwen

Харнесс обнаруживает задачи по `task.json`. Внутренний цикл каждой задачи выполняет `ReActAgent` из openJiuwen. Конкурсная команда включает `B+C+D`, локальную маршрутизацию, планировщик F, ранний отказ и прямую публикацию проверенных ответов. По умолчанию используется одна сессия и модель `qwen3.8-27b-noreason`. Для контрольного прогона задайте `--mode baseline`.

## Структура проекта

[run_agent.py](run_agent.py) запускает конкурсный харнесс, а [benchmark.py](benchmark.py) предоставляет команды подготовки, запуска и проверки локальных прогонов. Код харнесса находится в [contest_harness](contest_harness).

Сравнение штатной конфигурации с baseline на восьми и ста задачах сохранено в [результатах прогонов через API](docs/HARNESS_LIVE_API_RESULTS.md).

| Модуль | Ответственность |
| --- | --- |
| [cli.py](contest_harness/cli.py) и [scheduler.py](contest_harness/scheduler.py) | Настройка запуска, очередь задач, параллельные сессии и дедлайн. |
| [planning/](contest_harness/planning) | Предварительный анализ задач, маршрутизация, прогноз стоимости, допуск и отложенные повторы. |
| [agent/](contest_harness/agent) | Попытка openJiuwen ReAct, контекст, прокси модели и публикация проверенного ответа. |
| [workspace/](contest_harness/workspace) | Загрузка входов, инструменты, песочница, проверка формата и доказательства прохождения тестов. |
| [telemetry/](contest_harness/telemetry) | Резервирование общего бюджета, сверка токенов с прокси и трасса JSONL. |
| [evaluation/](contest_harness/evaluation) | Подготовка чистых копий, независимая оценка ответов, отчёты и экспорт наблюдений для планировщика. |

CLI загружает настройки прокси и настраивает журнал SDK до запуска сессий. Планировщик передаёт задачу исполнителю, а транспорт резервирует бюджет перед каждым HTTP-запросом. Исполнитель проверяет результат и атомарно публикует `answer.txt` до освобождения сессии. Пакет `evaluation` подключается отдельно для локальной проверки. Трасса и манифест стенда содержат отпечатки всех исходников харнесса, в том числе модулей, вызываемых через точки входа. Пакет [src/openjiuwen_challenge](src/openjiuwen_challenge) обслуживает регистрацию команды через MCP.

## Настройка, сборка и запуск жюри

Передайте `LLM_BASE_URL` и `LLM_API_KEY` через окружение. `LLM_BASE_URL` — базовый URL API с префиксом вроде `/v1`. Для локального запуска можно использовать игнорируемый Git файл `.env` по шаблону `.env.example`. Переменные процесса имеют приоритет. Для выбора модели задайте `LLM_MODEL` из списка в [AGENTS.md](AGENTS.md).

Для сборки из текущего дерева используйте отдельный чистый снимок. Команда включает содержимое отслеживаемых файлов и новых файлов, которые Git не игнорирует. Для финального коммита можно использовать `git archive HEAD`.

```bash
BUILD_TREE=$(mktemp -d)
git ls-files --cached --others --exclude-standard -z \
  | while IFS= read -r -d '' file; do
      if [ -e "$file" ] || [ -L "$file" ]; then printf '%s\0' "$file"; fi
    done \
  | tar --null -T - -cf - | tar -xf - -C "$BUILD_TREE"
du -sk "$BUILD_TREE"
/usr/bin/time -p docker build --no-cache -t openjiuwen-harness:local "$BUILD_TREE"
docker images openjiuwen-harness:local --format '{{.Repository}}:{{.Tag}} -> {{.Size}}'
```

В Docker закреплены Python 3.12.12 slim-bookworm по тегу и digest, openJiuwen 0.1.16.post20, остальные прямые и транзитивные Python-зависимости и libseccomp2. Пакеты скачиваются на этапе сборки. Список установленных пакетов проверяется командами `python -m pip freeze` и `python -m pip check`. [Dockerfile](Dockerfile) · [Ограничения версий](requirements-linux.txt)

Перед запуском задайте абсолютный путь `TASKS_DIR` к доступной на запись копии задач. В `PROXY_NETWORK` укажите изолированную Docker-сеть с доступом к прокси организаторов. Например, используйте `--internal` сеть с выделенным TCP-реле до единственного адреса и порта прокси. Контейнер харнесса подключается только к внутренней сети. Сохраните исходное имя HTTPS-хоста для SNI и проверки сертификата. Перед замером проверьте достижимость прокси и отсутствие маршрута во внешнюю сеть в контейнере агента.

```bash
docker run --rm --pull never --network "$PROXY_NETWORK" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges --pids-limit 512 --cpus 4 --memory 16g \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS_DIR:/data/tasks:rw" openjiuwen-harness:local --tasks-dir /data/tasks
```

`ENTRYPOINT` выполняет `python /app/run_agent.py --tasks-dir /data/tasks` из `/app`. План строится для всех задач до первого обращения к модели. Локальный лимит можно задать через `HARNESS_TOKEN_BUDGET` или `--local-budget`. Трасса по умолчанию сохраняется в новом каталоге `/tmp/openjiuwen-run-*`. Для дополнительного JSONL-журнала укажите `--results-file` или `OUT` с путём к файлу рядом с подкаталогами задач или за пределами `--tasks-dir`. Каждая запись включает идентификатор прогона и синхронизируется после попытки. Ответ атомарно сохраняется в `/data/tasks/<каталог-задачи>/answer.txt`. Для `coding` исходники остаются в `workspace/`, а исходные тесты сохраняются. Песочница Python использует Linux Landlock ABI 3 или новее и seccomp.

Для штатного запуска можно указать `HARNESS_ROUTING_PROFILE` и `HARNESS_PLANNING_HISTORY` с путями вне каталога задач. Профиль подключает калиброванный каскад. Эскалация допускается при положительной ожидаемой полезности и известном доступном остатке.

## Локальный стенд сравнения

Для стенда нужен Python 3.12. Для нативного прогона установите `requirements.txt`. На Linux проверка Python-кода использует Landlock и seccomp, на macOS — `sandbox-exec`. При запуске в Docker используйте уже собранный локальный образ. Команда `run` передаёт в контейнер только подготовленные задачи и отдельный каталог для трассы. Для реального замера установите `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL` в окружении. Сеть контейнера должна давать доступ только к прокси организаторов.

```bash
PY="$PWD/.venv/bin/python"  # либо python3.12
HISTORY="$PWD/logs/baselines/task-dir-100-20261110-133659-mCjShG"
mkdir -p "$PWD/logs/experiments"
SERIES=$(mktemp -d "$PWD/logs/experiments/baseline.XXXXXX")
BASELINE="$SERIES/history"
RUN_DIR="$SERIES/candidate"
ARCHIVE="$HISTORY/input-task-dir.zip"

"$PY" benchmark.py report --source-run "$HISTORY" --run-dir "$BASELINE"

# 1. Подготовка. Для публичных примеров задайте ARCHIVE с путём к task-dir.zip.
"$PY" benchmark.py prepare --archive "$ARCHIVE" --run-dir "$RUN_DIR"

# 2. Прогон. Сеть PROXY_NETWORK настраивается отдельно.
LLM_MODEL=qwen3.8-27b-noreason "$PY" benchmark.py run \
  --run-dir "$RUN_DIR" --image openjiuwen-harness:local \
  --network "$PROXY_NETWORK" --timeout 3600 --baseline "$BASELINE"

# 3. Независимая проверка после остановки агента, включая частичный прогон.
"$PY" benchmark.py check --archive "$ARCHIVE" --run-dir "$RUN_DIR"
```

Для нативного прогона уберите `--image` и `--network`. Если локальный Python не может запустить песочницу, выполните шаг 3 в контейнере без сети. Каталог отчёта и эталоны подключаются только к проверяющему контейнеру.

```bash
docker run --rm --network none --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges --pids-limit 512 --cpus 4 --memory 16g \
  -v "$PWD/benchmark.py:/app/benchmark.py:ro" \
  -v "$PWD/contest_harness/evaluation:/app/contest_harness/evaluation:ro" \
  -v "$ARCHIVE:/data/examples.zip:ro" -v "$RUN_DIR:/data/run:rw" \
  --entrypoint python openjiuwen-harness:local /app/benchmark.py check \
  --archive /data/examples.zip --run-dir /data/run
```

`prepare` и `check` также принимают `--source-dir /path/to/original-tasks` вместо `--archive`. Для нового эксперимента выбирайте ещё один каталог и повторяйте все три шага. `run --proxy-budget ЧИСЛО` записывает внешний лимит для отчётности. `run --local-budget ЧИСЛО` включает локальный допуск в агенте. `--timeout` задаёт предел времени работы процесса. Для управляемого двойника укажите `--proxy-kind test-double`, чтобы его результаты были явно отмечены в манифесте. `check` возвращает 1, если хотя бы один ответ не прошёл проверку, и всё равно публикует оценку и отчёт.

`run` и `check` автоматически собирают отчёт в каталоге текущего прогона. После жёсткого прерывания или для повторной генерации укажите новый каталог.

```bash
"$PY" benchmark.py report --source-run "$RUN_DIR" \
  --run-dir "$SERIES/recovered" --baseline "$BASELINE"
```

Состав и единицы артефактов описаны в [схеме стенда](docs/HARNESS_BENCHMARK_ARTIFACTS.md).

## Режимы A и B

`run_agent.py` и `benchmark.py run` принимают `--mode baseline|A|B`. `baseline` использует полную историю и общий список инструментов. Стенд по умолчанию запускает этот режим. A сохраняет полную историю и подбирает инструменты по типу задачи. B использует те же инструменты и сокращает окно запроса через `ContextEngine.register_window_mutator` в openJiuwen 0.1.16.post20.

B хранит исходную историю в буфере сессии SDK на 8 192 сообщения. Состояние хранится в памяти отдельно для каждой задачи. Оно включает инструкцию, явно названный план при наличии, статус, предыдущего кандидата, остаток локального бюджета, последние наблюдения по файлам, правки, результаты и ошибки. После записи файла предыдущее чтение этого пути и проверки предыдущей ревизии теряют актуальность. Следующее чтение подхватывает новые данные. При сжатии B сохраняет текущий результат проверки или указывает, что тесты нужно запустить снова.

Бюджет истории в запросе B составляет 8 192 байта в оценке сериализации SDK. Системная подсказка, исходная инструкция и схемы инструментов учитываются отдельно. При сокращении до 2 304 байт бюджета истории выделяется на компактное состояние. B выбирает целые группы вызовов с результатами, учитывая их актуальность, давность и размер. Для крупных исключённых результатов использует помеченные выдержки. Вызовов модели для сжатия нет. Фактические байты сообщений и схем записываются отдельно на границе HTTP.

Для сравнения подготовьте две копии одних входов. Запустите их с `--mode A` и `--mode B`, с одинаковыми моделью и локальным лимитом, затем оцените обе. При запуске и проверке B укажите `--baseline` с каталогом оценённого A. Команда воспроизведения сценариев с HTTP-двойником есть в [статусе этапа 04](docs/HARNESS_IMPLEMENTATION_STATUS.md).

## Компактный вывод и лимиты генерации

`--mode B+C` добавляет к B компактные списки, чтение, буквальный поиск `search_text` и вывод Python. Скрипт получает код завершения. Для стандартной сводки тестов харнесс показывает итог и подтверждённые количества. При неизвестном формате остаются диагностическая выдержка и доступ к расширенному выводу. Одинаковый вывод повторного вызова ссылается на сохранённый результат. Повторяющиеся строки консоли сокращаются в превью.

`output_details` принимает идентификатор из пометки `Details` и `range` со значением `diagnostic` или диапазоном байтов UTF-8, например `0:1024`. Верхняя граница диапазона исключается. Один запрос возвращает до 4 КиБ данных. Успешные результаты хранятся целиком в каталоге попытки под `/tmp`. Лимит расширенного Python-вывода и чтения файла составляет 2 МиБ на операцию, общий лимит хранилища составляет 64 МиБ. При превышении лимита инструмент явно сообщает об ошибке. Для больших файлов можно читать нужные диапазоны через Python. Ссылки на результаты действуют до завершения попытки.

`--mode B+C+D` выбирает один из пяти лимитов на каждом шаге. Лимиты выражены в токенах генерации. Любой из них можно переопределить флагом `--generation-limit PROFILE=TOKENS` в `run_agent.py` или `benchmark.py run`. Допустимое значение ограничено профилем модели из [профилей моделей](contest_harness/agent/model_profiles.py).

| Профиль | Лимит | Когда применяется |
| --- | ---: | --- |
| `short` | 160 | После успешного вычисления или запуска тестов |
| `analysis` | 768 | Первый шаг задачи без правок кода |
| `structured` | 384 | Чтение и поиск вне coding, переход к проверке после записи |
| `code` | 1 536 | Первый шаг coding и работа с исходниками |
| `debug` | 2 048 | После ошибки инструмента |

D проверяет исходный `finish_reason`, схему аргументов, идентификаторы вызовов и наличие непустого ответа при сдаче. После обрезания или ошибки структуры он запрашивает новый полный вызов с лимитом как минимум на уровне `code` и `debug`. Допускается одна попытка восстановления на шаг и две на задачу. Каждый запрос проходит общий бюджетный допуск. Используются обычные схемы инструментов и локальная проверка JSON-аргументов.

Для сравнения последовательно запустите `B`, `B+C` и `B+C+D` на свежих копиях одного набора с одинаковыми моделью и `--local-budget`. Трасса и отчёт разделяют байты вывода инструментов, входные и выходные токены, обращения за деталями, обрезания и запросы восстановления.

## Проверка и публикация ответа

`submit_answer` — стандартный путь сдачи во всех режимах. Формат определяется по инструкции. Поддерживаются, в частности, десятичные целые, точные слова, однострочные значения и JSON с явно перечисленными обязательными полями. Харнесс записывает итог с завершающим LF. Аргументы инструментов проверяются по объявленной схеме до исполнения. Абсолютные пути, выход из рабочего каталога, символьные ссылки и служебные файлы закрыты для обычных файловых инструментов.

В журнале `answer.validated` отдельно хранит результаты проверки формата и семантики. Значения `confirmed`, `failed` и `unverified` различают подтверждение, установленную ошибку и отсутствие надёжной проверки. Для поддерживаемых однозначных инструкций контроллер независимо вычисляет целочисленное выражение, суммирует столбец CSV или извлекает именованное поле из указанного файла. Сложное условие может потребовать обычной сдачи с `unverified`. Если инструкция требует подтверждения до сдачи, этот статус блокирует публикацию.

Для coding контроллер сверяет байты исходных тестов и проверяет запуск после последней правки. Поддерживаются прямые команды запуска оригинального Python-скрипта без аргументов и однозначно обнаруженный исходный тестовый скрипт. Для остальных команд проверка может остаться `unverified`. Код изменяется в рабочем каталоге до записи ответа. Проверка на исходных тестах и баллы независимого оценщика сохраняются отдельно.

При запуске на повторно используемом наборе прежние канонические ответы удаляются. Используйте свежие копии, чтобы сохранить результаты предыдущих прогонов. Явная запись `write_file(path="answer.txt", content=...)` из coding-задачи с `workspace/` передаёт содержимое этого вызова тому же валидатору и сразу пишет канонический файл. Существующий файл в `workspace/` не читается при сдаче. Текст финального сообщения модели сам по себе не публикуется.

Флаг `--direct-publish` в `run_agent.py` и `benchmark.py run` позволяет пропустить отдельный вызов `submit_answer` после инструмента, когда контроллер подтверждает формат и семантику. При неоднозначности агент продолжает стандартную сдачу. Для сравнения запустите один режим агента на двух свежих копиях с одинаковыми бюджетом и моделью и включите флаг только на второй копии.

## Маршрутизация и каскад

E1 сохраняет исходный выбор модели и инструментов. `--routing` включает E2. Маршрут `LOCAL` публикует ответ после проверки формата и локального решения для однозначного целочисленного выражения, явной суммы по CSV с поддерживаемыми фильтрами или единственного именованного поля в указанном файле. Остальные задачи идут через ReAct. Набор инструментов зависит от типа, маршрута и признаков файлов. Например, поиск простого значения в одном небольшом Markdown-файле получает инструменты чтения и поиска.

`CHEAP_LLM` использует `LLM_MODEL`. Профиль `--routing-profile` добавляет сравнение моделей по доле независимо подтверждённых решений и среднему расходу на одинаковых задачах каждого типа. Более точная модель или более экономная модель при равной точности может получить маршрут `SMART_LLM` на сложной задаче, если ожидаемая выгода положительна и хватает известного лимита. Для признаков сложности используются длина инструкции, операции, число и объём файлов и число исходников. Профиль строится на отдельном наборе, из сопоставимых контрольных прогонов через прокси.

```bash
python scripts/calibrate_task_router.py --initial-model "$LLM_MODEL" \
  --output /tmp/router-profile.json /tmp/cal-initial /tmp/cal-alternative
```

`--routing --cascade --routing-profile /tmp/router-profile.json --local-budget TOKENS` включает E3. `CASCADE` начинает с `LLM_MODEL` и допускает один переход после отклонённого кандидата, ошибки генерации или исчерпания числа шагов при наличии содержательного прогресса. Одиночная ошибка инструмента и окончание попытки без прогресса вследствие ошибок сами по себе не подходят. Начальная попытка с измеренной альтернативой ограничена восемью шагами в E2 и E3. Лимит задаётся `--cheap-steps`. Остальные попытки используют стандартные 20 шагов.

При переходе контроллер требует положительную оценку `P_smart * reward - lambda * (C_smart + C_verify)` и известный доступный резерв. `P_smart` опирается на успехи второй модели на задачах, где первая ошиблась, со сглаживанием по типу текущего исхода. Это приближение по парным самостоятельным прогонам. `C_smart` включает средний измеренный расход и оценку входа для передачи состояния. Локальная проверка даёт `C_verify = 0` в токенах. `--cascade-lambda` задаёт цену токена в баллах, по умолчанию 0,00025. HTTP-допуск отдельно резервирует каждый запрос по фактическому размеру. Все вызовы обеих попыток входят в общий расход.

Для сравнения подготовьте три свежие копии одного набора. В `benchmark.py run` задайте одинаковые модель, режим и бюджет, а затем передайте соответственно без флагов маршрутизации, с `--routing --routing-profile PATH` и с дополнительным `--cascade`. Выполните `benchmark.py check` с отдельным источником эталонов. Сводка отражает распределение маршрутов и моделей, локальные баллы, доли и расход до и после перехода. [Схема артефактов](docs/HARNESS_BENCHMARK_ARTIFACTS.md)

## Планировщик F и параллельные сессии

`--planner F` оценивает все задачи до первого запуска ReAct и сортирует их по `reward / estimated_cost`. При доступной оценке успеха числитель равен `reward * p_success`. Равные приоритеты сохраняют исходный порядок каталогов. `--planner control` строит тот же прогноз для сравнения и выполняет задачи в прежнем порядке. По умолчанию работает одна сессия.

Оценка берёт медиану полного расхода по типу задачи, начальному маршруту и модели из трёх или более сопоставимых наблюдений. Полный расход включает все вызовы попытки. Для редких сочетаний запасной прогноз суммирует первый и повторные запросы, дополнительный вход для контекста, восстановление генерации, проверку тестов с участием модели и возможный переход на другую модель. Локальная проверка учитывается в миллисекундах. У маршрута LOCAL нулевой токенный прогноз и нижняя граница знаменателя 0,1 для сортировки.

Перед стартом F сверяет прогноз и оценку резерва первого вызова с остатком, который уже учитывает измеренный расход, удержанный резерв и запросы в полёте. Используется большая из двух оценок. Если задача не помещается, F отмечает причину и проверяет следующую. Транспорт по-прежнему резервирует каждый фактический запрос. При неизвестном числовом лимите F сортирует задачи и продолжает до остановки прокси.

Экспортируйте историю из отдельно проверенных прогонов и держите её вне входов оцениваемых задач. Для отчётов прежних этапов сначала пересоберите их командой `benchmark.py report` в новом каталоге. Наблюдения с совпадающим `task_id` или отпечатком инструкции исключаются. В сопоставимых группах с 20 и более независимыми исходами с прокси организаторов используется сглаженная историческая доля успеха. Меньшая выборка даёт N/A. Для сравнения подготовьте свежие копии и передайте обоим режимам одинаковый профиль истории, модель, настройки и лимит. [Формат траекторий](docs/HARNESS_BENCHMARK_ARTIFACTS.md)

```bash
python benchmark.py planning-history --output /tmp/planning-history.jsonl /tmp/checked-history
python benchmark.py run --run-dir "$CONTROL" --mode B+C --local-budget 7500 \
  --planner control --planning-history /tmp/planning-history.jsonl
python benchmark.py run --run-dir "$F" --mode B+C --local-budget 7500 \
  --planner F --planning-history /tmp/planning-history.jsonl --baseline "$CONTROL"
```

`--sessions N` принимает от 1 до 5. Значения выше 1 включают F. Для сравнения подготовьте две свежие копии, укажите `--planner F` в обеих и меняйте только `--sessions`. Каждая сессия забирает задачу из общей очереди один раз и получает отдельные ReAct-контекст, рабочий каталог и временные файлы инструментов в `/tmp`. Готовый ответ сразу публикуется в своём `answer.txt`.

Если задаче временно мешает резерв активных запросов, F может взять следующую подходящую задачу. Каждый запрос повторно проверяет общий остаток непосредственно перед отправкой. В параллельном режиме запрос может ждать сверки других резервов в пределах своего 120-секундного таймаута. После трёх подряд ошибок прокси по задачам или HTTP 401, 402, 403, 429 очередь перестаёт выдавать новые задачи с вызовами модели. Активные сессии могут завершить работу. Одна сессия сохраняет остановку после первой ошибки прокси.

Харнесс прекращает запуск и отменяет незавершённые задачи по `--run-timeout SECONDS` (по умолчанию 3 570 с) или SIGTERM. Уже опубликованные файлы доступны сразу. Суммарные длительности вызовов и инструментов могут превышать полное время прогона, поскольку сессии выполняются одновременно. Отчёт показывает полное время, отдельное время ожидания резерва и пик активных сессий.

## Трассировка расхода токенов

Для локального ограничения запускайте `python /app/run_agent.py --tasks-dir /data/tasks --local-budget 5000.1`. Лимит задаётся в выходном эквиваленте с точностью до одной десятичной цифры. Харнесс хранит целые десятые и считает `input_tokens + 10 * billable_output_tokens`. Весь кешированный вход уже входит в `prompt_tokens` или восстанавливается из полного разбиения на cache hit/miss. Для reasoning вложенный счётчик обычно обозначает часть `completion_tokens`. Если `total_tokens` равен сумме входа, выхода и явно указанного reasoning, отдельный reasoning добавляется один раз. При неоднозначном пересечении счётчиков расход отмечается как `unknown`.

Перед отправкой запрос занимает общий резерв. Оценка входа использует байты UTF-8 всего HTTP-тела с сообщениями и схемами, плюс 32 токена на сообщение или схему и фиксированный запас на шаблон прокси. Для обеих моделей `-noreason` предел генерации равен 2 048 токенам, запас шаблона — 256. Для вариантов с рассуждениями предел равен 4 096, запас шаблона — 512 и в резерв добавляется ещё 4 096 выходных токенов на возможный отдельный reasoning. Оценка предполагает один текстовый ответ, токенизатор на уровне байтов и соблюдение лимита генерации прокси. Реальный шаблон и политика прокси могут дать превышение. Каждое превышение оценки входа или выхода регистрируется по `usage`. Лимит расхода ограничивает локальный допуск по этой оценке.

Точный `usage` заменяет резерв фактом. Если учтена лишь часть расхода, резерв удерживается для неизвестной части. Таймаут, отмена и сбой после возможной отправки без статистики удерживают весь резерв. Подтверждённый отказ до отправки освобождает резерв. Запрос выполняется максимум 120 секунд, автоматические повторы отключены, после ошибки прокси последовательный прогон завершается. В D планировщик сначала выбирает задачи, для которых помещается прогноз целиком. Если остаются задачи, для которых хватает только на первый запрос, он допускает одну такую задачу за раз. Транспорт уменьшает лимит обычного запроса при необходимости. Восстановление ответа требует полного резерва. Если прокси сообщает расход выше полного резерва уже отправленного запроса, харнесс фиксирует фактический расход и блокирует дальнейшие LLM-вызовы с локальным лимитом. Учёт, предел генерации и таймаут действуют и при запуске без `--local-budget`.

Флаг `--trace-file` включает отдельный JSONL-поток. Укажите новый файл вне каталога задач или `-` для вывода в stderr. Каждая строка записывается сразу. При ошибке записи харнесс отключает подробную трассировку и продолжает считать расход для отчёта в stdout.

| События | Данные для сравнения |
| --- | --- |
| `run.started`, `run.tasks_discovered`, `run.finished` | Версии Python и openJiuwen, отпечатки файлов харнесса, порядок задач, итоговый расход и число пропущенных из-за остановки задач. |
| `task.started`, `task.loaded`, `task.finished` | Идентификатор сессии, место задачи в очереди, тип, `reward`, отпечаток условия, статус, время и расход по задаче. |
| `planning.task`, `planning.ready`, `planning.decision` | Признаки и прогнозы до начала работы, исходный и плановый порядок, остаток и причина отказа в допуске. |
| `llm.started`, `llm.denied`, `llm.waiting_for_budget`, `llm.request`, `llm.finished` | Резерв и решение о допуске, модель, параметры генерации, размеры и отпечатки сообщений и схем, статистика прокси, сверка с резервом, время и ошибки. |
| `tool.started`, `tool.finished` | Вызванный инструмент, размеры аргументов и результата, время выполнения и статус. |
| `answer.validated`, `answer.saved` | Раздельные вердикты, решение о допуске, источник кандидата и факт сохранения. |

Связывайте события по `run_id`, `task_index` и `call_id`. `context.delta` показывает общий префикс сообщений и изменение размера контекста и схем инструментов. `proxy_usage` содержит числовые счётчики из HTTP-ответа, а `usage` содержит расход с пересчётом по регламенту. `exact_tenths` равен `null` при неизвестном расходе, `measured_tenths` хранит наблюдаемую часть, `held_tenths` — удержанный резерв. Размеры отдельных сообщений и схем выражены в байтах. Промпты, ответы модели, код, содержимое файлов и учётные данные представлены только метаданными либо исключены из событий.

```bash
jq -c 'select(.event == "llm.finished") | {task_id, call_id, model, usage, input_tokens_change}' \
  "$RUN_DIR/trace.jsonl"
jq -c 'select(.event == "llm.request") | {task_id, call_id, roles: .context.by_role, delta: .context.delta}' \
  "$RUN_DIR/trace.jsonl"
```

## G — ранний отказ

`--early-stop` включает G поверх планировщика F. Флаг поддерживают `run_agent.py` и `benchmark.py run`. Число сессий задаёт `--sessions`. Команда жюри использует исходную конфигурацию, пока флаги отсутствуют.

G подтверждает блокер для явно указанного обязательного входного файла или каталога, если проверка пути в рабочем каталоге показывает отсутствие либо несовместимый тип ресурса. Условные инструкции, запасные источники, ссылки и неоднозначные пути передаются в ReAct. Проверка занимает локальное время и обходится без LLM-вызова. Сообщения модели о недостающих сведениях и предполагаемой невыполнимости сохраняются как `NEED_MORE_INFO` и `UNSOLVABLE_SUSPECTED`. `UNCERTAIN` охватывает попытку без ответа, лимит шагов или отклонённый кандидат. Прогноз стоимости и отказ в резерве дают `BUDGET_EXCEEDED` с разными основаниями. Ошибки генерации, прокси и прерывание дают `FAILED`. `DONE` фиксирует публикацию `answer.txt`.

После основного прохода G может повторить подходящую попытку один раз при известном достаточном остатке и положительной прогнозной отдаче. Вероятности для повтора заданы эвристически по исходу. В прогноз входят будущие затраты и резерв первого запроса с учётом передаваемого состояния. Для coding сохраняются изменения и история проверки текущей ревизии. Каскад использует собственное правило эскалации.

Скрипт сравнения создаёт свежие копии, запускает F и G с одинаковыми условиями и применяет независимую разметку после прогона. Для локального HTTP-двойника установите зависимости тестов. Для живого замера используйте `--proxy-kind organizer`, настройки прокси и выделенные лимиты.

```bash
PY="$PWD/.venv/bin/python"

EXP=$(mktemp -d "$PWD/logs/stage-10/replay.XXXXXX")
"$PY" scripts/compare_early_stop.py --output "$EXP/double" --proxy-kind test-double \
```
